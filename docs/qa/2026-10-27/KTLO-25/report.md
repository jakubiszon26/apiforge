## What disagreed

`components/product.afs`, line 15, column 28:

```
  @config({ contractId: "Product", type: "object" })
  export product: object = fetch_product.body
```

The export promises an object of the `Product` contract and takes the whole
response of the `fetch_product` request. A request's response carries the
contract its own configuration names, and `fetch_product` named none. The
board's connection rule, which the analysis also applies to code, lets a slot
with a contract take only a source with the same contract, so the export was
reported with "The value's type does not match this input". The value itself
was right: the demo API returns a product.

The acceptance test found a second document with the same defect, which the
issue did not name: `components/add-to-cart.afs`, line 30, column 25,
`export cart: object = fetch_cart.body` (contract `Cart`, from the request
`fetch_cart`, which named no contract either).

The fix gives the two requests the contract their export promises:
`fetch_product` returns a `Product` and `fetch_cart` a `Cart`. Their sources
now print `contract "Product"` and `contract "Cart"` inside the request.
Nothing else in the demo changes. The same field is added to the frozen
version-one shop sources, because the demo must match the generated project
fixtures node for node, and the fixtures are regenerated by the converter.
