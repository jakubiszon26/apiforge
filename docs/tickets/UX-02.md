# UX-02: Run mode is a setting; the Run button reads *Run simulation* or *Run live*

- Size: S · Owner review: 20 min · Risk: `visible UI`, `default`
- State: Analysis (issue #99) · decisions taken by the owner on 2026-11-02 on
  the UX-00 mock-up (#97, approved as a whole) · acceptance criteria posted
  on #99 on 2026-11-02 and carried below · no decision open · UX-1 sprint,
  wave 1 ([plan](../sprints/ux-1.md)) · **before UX-04** (both touch the
  header's run controls) · labelled `ready:opus`
- Analysis model: Fable · Implementation model: Opus

## Goal

The window remembers, per project, whether a run is a simulation or goes to
the live API. The header's one Run button runs that mode and says which:
*Run simulation* in violet, *Run live* in the accent. The mode is chosen in
the chevron menu beside the button and holds until it is changed.

## What the owner will see

- New: the Run button reads *Run simulation* (violet fill, white text) or
  *Run live* (accent fill, as *Save*). A chevron at its right, named *Run
  options*, opens the menu: the caption RUN MODE; *Simulation* with the hint
  *Sample responses; no request is sent.*; *Live* with the hint *Requests go
  to the project's API.*; the line *The Run button runs this mode until you
  change it.*; a separator; *Review legacy runs*. The two mode items are
  indented 8 px from the caption (the owner's addition). The button's hover
  text names the mode: *Simulate the selected scenario or component with
  sample responses, including unsaved valid code* / *Send the requests of
  the selected scenario or component to the API, including unsaved valid
  code*.
- Changed: the SIMULATION badge in Run results takes the same violet
  (`theme::SIMULATION`, 112 · 76 · 182) instead of the link blue; the
  button and the badge share the constant. The text button *Run options*
  becomes the chevron, which gives the project name its room back at 960 px.
- Removed or hidden: the one-off item *Run live requests* leaves the menu;
  the mode replaces it (decided).
- Migrated or converted: nothing. The mode is kept in a new file
  `run-mode.json` beside `agent-consent.json` in the person's configuration
  directory; the project format and the manifest are unchanged (decided).
- Default behaviour that changes: none in effect. A project never set starts
  in Simulation, which is what *Run* does today; once *Live* is chosen it is
  remembered for that person and project across windows and restarts.
- While the window observes (MCP-08a): *Live* in the menu is disabled with
  the hover *Live requests are not sent from this window while another
  process holds the project.*, as the old item was, and the button reads and
  runs *Run simulation* whatever the stored mode. The stored mode is kept and
  returns when the window holds the project again. (The agent's decision:
  a *Run live* button that only shows an error notice would be worse.)
- MCP-09's *Live allowed* badge and consent are unchanged (decided): they
  concern the agent's requests, not the window's own.

## Acceptance criteria

Criteria 1–6 are the ones posted on #99 (2026-11-02), each made testable;
7–9 are added by this analysis. Tests are in
`crates/apiforge-desktop/src/folder/acceptance_tests.rs`, `mod ux02`, on the
demo shop project with an isolated configuration directory
(`use_configuration_directory`), unless a criterion says otherwise.
"Clicking" is a pointer click on the named widget after `settle`.

1. The Run button reads *Run simulation* when the mode is Simulation and
   *Run live* otherwise; *Run simulation* is filled with the violet
   `theme::SIMULATION` (`112 · 76 · 182`), *Run live* with the accent, and
   the SIMULATION pill in Run results takes the same constant. Tests: the
   labels and the mode they run through
   `ux02_criterion_1_the_button_reads_its_mode` (a project never set shows
   *Run simulation*; after *Live* is chosen, *Run live*); the colour by a
   unit test of the constant and of the fill the button is built with
   (`ux02_criterion_1_simulation_is_one_violet`); the colour on screen by
   the QA captures, since interaction tests do not read pixels (ADR 0013,
   decision 8).
2. A chevron at the right of the Run button, named *Run options*, opens the
   menu with *Simulation* and *Live*, each with its hint, and *Review legacy
   runs*; *Run live requests* is nowhere; the left edge of *Simulation* and
   of *Live* is at least 8 px right of the RUN MODE caption's left edge (the
   owner's "a little more left margin"); on a scenario's tab at 960 × 540
   the project name's label is at least as wide as *Demo shop* laid out in
   the header's font (whole, not truncated). Tests:
   `ux02_criterion_2_the_chevron_opens_the_menu`,
   `ux02_criterion_2_the_mode_items_are_indented`,
   `ux02_criterion_2_the_project_name_is_whole_at_960`.
3. The mode is kept per person and per project in the app's configuration,
   as MCP-09's consent is: after *Live* is chosen,
   `apiforge/run-mode.json` in the configuration directory names the
   project's manifest id with `live`; a second harness on the same project
   and directory starts with *Run live*; a harness on another project in the
   same directory starts with *Run simulation* (a project never set); the
   project folder is byte-identical before and after the choice. Test:
   `ux02_criterion_3_the_mode_is_kept_per_project_and_the_project_is_untouched`.
   Unit tests in `run_mode.rs`, as `consent.rs` has them: an unreadable,
   newer or oversized file is Simulation; a write keeps the other projects'
   entries; without a directory the choice lasts for the window.
4. The Run button runs the chosen mode: clicking *Run simulation* gives a
   report in Simulation and a listener at the project's base URL receives
   no connection; clicking *Run live* gives a report in Live and the
   listener receives the request. *Run live* where live is not possible
   behaves as today's live run does: refined to the three cases the code
   has — while the window observes (MCP-08a) the button reads and runs *Run
   simulation* whatever the stored mode, *Live* in the menu is disabled with
   the hover *Live requests are not sent from this window while another
   process holds the project.*, and *Run live* is back after *Take back*;
   with the journal unavailable, the confirmation prompt of today; with
   invalid code, *Run this version* as today. Tests:
   `ux02_criterion_4_the_button_runs_the_chosen_mode`,
   `ux02_criterion_4_observing_runs_a_simulation` (with `mod mcp08b`'s
   spawned server and hand-over); the two prompts are covered by their
   existing tests, re-pointed at *Run live*.
5. MCP-09's *Live allowed* badge is unchanged apart from sitting beside
   *Run live*: its text, colour, hover and the consent it reflects are
   today's; `mod mcp09`'s tests pass unchanged. Test:
   `ux02_criterion_5_live_allowed_is_unchanged`.
6. The implementation matches `ux02-*` (the table above) at 960 × 540 and
   1600 × 1000: the QA report compares the captures, on Linux and from the
   Windows CI artifacts; the verification commands of the development guide
   pass.
7. Added: the header fits. At 960 × 540 and 1600 × 1000, in Code, Diagram
   and Split, with *Live allowed* shown, on a scenario's tab and on a
   component's tab (*Publish* present), the project name, *Code*, *Diagram*,
   *Split*, *Save*, *Save all*, *Publish*, *Run options* and *Run
   simulation* / *Run live* are within the window and disjoint. Test:
   `ux02_criterion_7_the_header_fits` with `assert_within_window` and
   `assert_disjoint`.
8. Added: a tab that cannot run (a text file, or no tab) keeps the *Runs*
   menu with *Review legacy runs* as today. Test:
   `ux02_criterion_8_the_runs_menu_is_unchanged`.
9. Added: the chevron and the button are reachable by Tab in the header's
   order and the chevron's accessible name is *Run options*. Test:
   `ux02_criterion_9_the_controls_are_accessible` (`accessibility_tests.rs`

## Estimate

S: complexity a little (a new store copied from `consent.rs`; the header's
width rule), regression potential low and tested: the run path does not

`live` the button passes. Every test that clicks *Run* or *Run live
requests* by label is renamed, about fifteen call sites in
`acceptance_tests.rs`, `component_run_tests.rs` and the interaction tests,
without an assertion changing. 20 owner minutes: a visible change covered by
captures. Lines about 500 (code 150, tests 250, QA report and this ticket).
Order: batch (a) with UX-01 and UX-03; **UX-04 starts after this ticket is
merged**, since it places its label beside *Cancel run* in the same
right-to-left row and measures the header with this ticket's wider button.

## Technical appendix

- `crates/apiforge-desktop/src/run_mode.rs` (new): `RunModeStore` modelled
  on `consent.rs::AgentConsent` — `load()`, `#[cfg(test)]
  in_configuration(dir)`, `mode(project) -> RunMode` (default Simulation),
  `set(project, mode)` — file `apiforge/run-mode.json`:
  `{ "version": 1, "projects": { "<manifest id>": { "mode": "simulation" |
  "live", "changedAt": "<RFC 3339 UTC>" } } }`, with the same best-effort
  rules (missing, unreadable, newer or oversized file is the default; an
  atomic write that reads the file again and replaces one entry; a newer
  file is never overwritten). No one-second re-read: the mode is the
  person's choice at this window, and the last writer wins as with
  preferences. Kept independent of `consent.rs` so MCP-09's tests and
  version semantics stay untouched. `FolderApp` holds it beside `consent`;
  `use_configuration_directory` (`folder/mod.rs`) points both at the test
  directory; `main.rs` loads it as it loads the consent.
- `theme.rs`: `pub const SIMULATION: Color32 = Color32::from_rgb(112, 76,
  182)`. `widgets.rs`: `ActionButton::fill(colour)` as the mock-up added it
  (a primary button in another fill; engaged `gamma_multiply(0.9)`).
  `report.rs::header_row`: the pill takes `theme::SIMULATION`.
- `folder/chrome.rs::header`, the right-to-left row: the chevron
  `widgets::action_menu(ui, widgets::icon_button(Icon::ChevronDown, "Run
  options"), menu)` first, then `ui.add_space(-item_spacing.x + 2.0)`, then
  `widgets::action(Icon::Play, label).primary()` with `.fill(SIMULATION)`
  for the simulation; the menu body as in the mock-up's `menu` closure
  (`widgets::caption("RUN MODE")`, two `selectable_value`s each in a
  `horizontal` after `add_space(8.0)`, `widgets::hint`s, separators, the
  line, *Review legacy runs*), named *Run options menu* with
  `widgets::name_menu`. The `reserved` width keeps the mock-up's
  measurement: plus the width of the mode label over *Run*, minus the width
  the text button *Run options* no longer takes. `let live = mode == Live &&
  !observing` decides the label, the fill, the hover and the `live` passed
  to `request_run`.
- The mock-up's `mock_ux00` switches are not merged; the review view
  `review_ux02_run_mode` is rewritten against the real controls and added to
  `testing::review`.
