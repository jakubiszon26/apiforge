# UX-03: The focus line turns grey; error marks appear after a pause in typing

- Size: S · Owner review: 10 min · Risk: `visible UI`, `removal`
- State: Analysis (issue #100) · decisions taken by the owner on 2026-11-02
  on the UX-00 mock-up (#97, approved as a whole) · acceptance criteria
  posted on #100 on 2026-11-02 and carried below · no decision open · UX-1
  sprint, wave 1 ([plan](../sprints/ux-1.md)) · before UX-11 (#216, #217),
  which touches the same editor · labelled `ready:opus`
- Analysis model: Fable · Implementation model: Opus

## Goal

The editor stops shouting while the person types: the accent line at the
gutter's edge becomes a quiet grey, and the red line numbers, dots and
underlines wait until typing has paused for 700 ms instead of returning on
every keystroke.

## What the owner will see

- Changed: the 2 px vertical line at the right edge of the gutter, shown
  while the editor has keyboard focus, is `theme::MUTED` grey instead of the
  accent (the "red line" of the finding). Keyboard focus stays visible.
- Changed: the error marks — the red line number and the dot in the gutter,
  the underline in the text and the message on hover — appear only once no
  text has been typed into the document for **700 ms** (the owner's "about
  0.5–1 s"). From the first keystroke that changes the text until then the
  gutter shows plain numbers and the text no underline; then the marks of the
  current analysis appear, without a mouse move.
- Unchanged: the PROBLEMS caption's status (*Unsaved changes · 2 errors*, red
  while the code is invalid) and the list under it keep following the
  analysis as today, 250 ms after the last keystroke (decided: "the PROBLEMS
  status is unchanged"). The board in Split still follows within 500 ms
  (ADR 0007); the analysis pause itself does not change. MCP-16's changed-line
  bars in the gutter are not error marks and are not delayed.
- Removed or hidden: nothing. The `removal` flag was given at ticketing when
  the "red line" was taken for a status line; the owner clarified it is the
  focus line, which stays, grey.
- Migrated or converted: nothing. Default behaviour that changes: none.

## Decisions taken (owner, 2026-11-02, quiz on the UX-00 mock-up, on #100)

> - The red line meant is the **vertical focus line** at the gutter's edge.
>   It becomes a **grey** line, so keyboard focus stays visible.
> - The PROBLEMS status is unchanged.
> - The error marks (red line numbers, dots, underlines) appear **after a
>   pause in typing** (about 0.5–1 s), not on every keystroke.
> - The mock-up was approved as a whole (`mock/ux-00` at `2c1fa79`, `ux03-*`).

The agent's choices under them, reported here: the grey is `theme::MUTED`
(107 · 107 · 107), the line keeps its 2 px; the pause is 700 ms
(`MARKS_DELAY`), separate from the analyser's 250 ms so that the board and
the Problems list keep ADR 0007's budget; while the pause runs no mark is
drawn (the old marks' positions would be wrong after the edit).

## Acceptance criteria

Criteria 1–4 are the ones posted on #100 (2026-11-02), each made testable;
5–7 are added by this analysis. Tests are in
`crates/apiforge-desktop/src/folder/editor_tests.rs` (the editor's existing
interaction tests), `mod ux03`, on the demo shop project in Code at
960 × 540 unless said otherwise. The posted "stepped clock" is the editor's
clock made injectable: `FolderApp::set_marks_clock` takes the instant the
rule reads as *now*, so a test steps it by hand and no test waits on the
real clock.

1. The vertical focus line at the gutter's edge is grey, never red, while
   the editor has keyboard focus, and absent without focus. Testable form:
   the stroke the editor paints is 2 px `theme::MUTED` when focused and none
   otherwise, through a `#[cfg(test)]` seam on `CodeEditor` that reports
   the last focus stroke (`ux03_criterion_1_the_focus_line_is_grey`); the
   colour on screen is a QA capture against `ux03-now` at both sizes, since
   interaction tests do not read pixels (ADR 0013, decision 8).
2. Red line numbers, gutter dots and underlines for an error appear only
   after a pause in typing of 700 ms, not on every keystroke: type
   `total = cart.body.` on a new line, let the analysis finish (`settle`)
   with the clock stepped by 300 ms — the editor marks no line
   (`FolderApp::marked_lines(document_id)` is empty) although the PROBLEMS
   status already counts the error; correct the line within the pause and
   settle — still no mark ever shown; type the error again and step the
   clock by 700 ms — `marked_lines` names the line and the layout job's
   underline covers the diagnostic's range. Tests:
   `ux03_criterion_2_no_marks_while_typing`,
   `ux03_criterion_2_an_error_corrected_within_the_pause_shows_no_mark`,
   `ux03_criterion_2_marks_follow_the_analysis_after_the_pause`.
3. The PROBLEMS status is unchanged: during the same edit the caption's
   status reads *Unsaved changes · N errors* in `theme::DANGER` 250 ms after
   the keystroke and the list names the line, as today. Test (regression):
   `ux03_criterion_3_the_problems_status_is_unchanged`; the existing
   Problems tests pass unchanged.
4. The implementation matches `ux03-now` (the line's place, the marks'
   places) and `ux03-no-focus-line` (nothing else moves) at 960 × 540 and
   1600 × 1000: the QA report shows the focused editor with the grey line,
   the editor mid-typing without marks and the settled state with the marks,
   on Linux and from the Windows CI artifacts; a design review view
   `review_ux03_editor_typing` renders the three states; the verification
   commands of the development guide pass.
5. Added: the pure rule and the repaint. `marks_due(last_typed:
   Option<Instant>, now, delay)` is true with no keystroke recorded, false
   699 ms after one, true at 700 ms; and the editor requests a repaint for
   the moment the marks are due, so they appear without a mouse move (the
   editor's `Shown` carries the remaining wait and `code_view` calls
   `request_repaint_after`). Unit tests: `ux03_criterion_5_marks_due_at_the_delay`,
   `ux03_criterion_5_a_repaint_is_requested_for_the_marks`.
6. Added: any change of the text by the editor counts as a keystroke —
   typing, paste, undo (Ctrl+Z) and redo each restart the pause; moving
   the caret, selecting and scrolling do not. Test:
   `ux03_criterion_6_only_text_changes_restart_the_pause`.
7. Added: nothing else moves. The analyser's `APPLY_DELAY` is still 250 ms;
   the existing tests of the board following the text (ADR 0007; smoke
   list 5) pass unchanged; MCP-16's changed-line bars show while typing
   (`mod mcp16` passes unchanged).

## Technical appendix

- `crates/apiforge-desktop/src/code.rs::paint_gutter`: the focus stroke
  `Stroke::new(2.0, theme::MUTED)` instead of
  `ui.visuals().selection.stroke.color`. Nothing else in the editor changes:
  it draws whatever `Context::diagnostics` holds.
- `folder/code_view.rs::code_view`: the diagnostics given to
  `code::Context` are `&snapshot.diagnostics` when `marks_due(…)` and `&[]`
  otherwise; the last text change is recorded beside the existing
  `self.analyser.typed(document_id, Instant::now())` call (line 235) in a
  `marks_quiet_at: HashMap<String, Instant>` on `FolderApp` — the analyser's
  own map cannot serve, it forgets the instant when the analysis starts.
  `publication.rs:168` (a model edit from the board) also calls `typed`;
  a board edit is not typing and does not touch `marks_quiet_at`. The
  remaining wait goes to `ui.ctx().request_repaint_after(wait)`.
  `MARKS_DELAY: Duration = 700 ms` in `code_view.rs`; the rule reads *now*
  from `FolderApp::marks_clock`, `Instant::now()` by default and the instant
  `#[cfg(test)] set_marks_clock` gave (the posted "stepped clock").
- The Problems caption (`diagnostics_panel`) is untouched; the mock-up's
  `mock_ux00::Status` and `no_focus_line` switches are not merged.
- Test seams: `#[cfg(test)] FolderApp::marked_lines(&self, document_id) ->
  Vec<usize>` (the lines the editor was last given diagnostics for, through
  `code::marked_lines`), and the focus stroke recorded by the editor in tests.
