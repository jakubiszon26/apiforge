## Goal

After one run, a check can be added for several fields from Run results
without running again: each *Check* adds its check at once, the results
stay usable, and the panel says how many checks wait for the next run.

## What the owner will see

- New: after *Check* on a field, its row reads *Check added* with a green
  tick where *Check* and *To variable* were; every other field still offers
  *Check* and *To variable*. The panel's bar reads *2 checks added · they run
  on the next run* in grey (for one: *1 check added · it runs on the next
  run*) where *Graph changed · results from an earlier version* appears
  today. The step list, the Outputs, Inputs and Request tabs, *Export* and
  the error policy stay usable; the board and the code keep showing the
  run's marks.
- Changed: adding a check no longer makes the results stale. Any other
  change to the document — typing, a block moved or added on the board, the
  error policy, a field assigned to a variable, a publish — makes them stale
  as today, with the amber *Graph changed* text, and the count no longer
  shows. Undoing a check takes the count down; undoing every check returns
  the results to fresh, with *Check* offered again.
- Unchanged: the board selects the new check card as it does today; the
  panel keeps the step whose outputs were shown. The next run runs the
  checks and starts a new count.
- Removed or hidden: nothing. Migrated or converted: nothing. Default
  behaviour that changes: none.

## Decisions taken (owner, 2026-11-02, quiz on the UX-00 mock-up, on #98)

> - Each *Check* adds at once and the results stay usable; checked fields
>   read *Check added* (`ux01-two-checks-960x540`).
> - When the only change is the added checks, the panel bar reads *N checks
>   added · they run on the next run* in grey. Any other change keeps
>   *Graph changed · results from an earlier version*.
> - There is no undo on the field: the edit is undone like any other edit.
> - The mock-up was approved as a whole (`mock/ux-00` at `2c1fa79`, `ux01-*`).

The agent's choices under them: the singular wording *1 check added · it
runs on the next run*; a checked row offers neither *Check* nor *To
variable*, as the approved capture shows.

## Acceptance criteria

Criteria 1–4 are the ones posted on #98 (2026-11-02), each made testable;
5–9 are added by this analysis. Tests are in
`crates/apiforge-desktop/src/folder/acceptance_tests.rs`, `mod ux01`, on the
demo shop project in Split at 960 × 540 unless said otherwise: run a
simulation with the header's run button, select the *Add to cart* step,
maximise Run results, and click the *Check* on the row of the named field
(the mock-up's `check` helper: the *Check* nearest the field's label).

1. *Check* on field A (`productId`) adds a check card and the panel stays
   usable: the scenario's source gains one field assertion (one more node
   in the graph, the same assertion *Check* adds today), the panel still
   shows *Add to cart*'s Outputs, the `productId` row reads *Check added*
   and offers neither *Check* nor *To variable*; *Check* on field B
   (`total`) adds a second card without a run and its row reads *Check
   added* too. Test: `ux01_criterion_1_two_checks_from_one_run`.
2. With only checks added since the run, the bar reads *N checks added ·
   they run on the next run* in grey (`theme::MUTED`): *1 check added · it
   runs on the next run* after the first, *2 checks added · they run on the
   next run* after the second, *Graph changed* absent. After any other
   edit — refined to one case each of typing a space into the code, moving
   a block on the board and choosing the other error policy — it reads
   *Graph changed · results from an earlier version*, the count is gone and
   the remaining *Check* buttons are disabled as today. Tests:
   `ux01_criterion_2_the_bar_counts_the_checks`,
   `ux01_criterion_2_another_change_makes_the_results_stale`.
3. Undo removes the last added check like any edit and the field's *Check
   added* reverts. Refined: the application's own undo (Ctrl+Z with the
   board focused, the gesture that undoes a block added from the library);
   after two checks one undo gives *1 check added* and `total` offers
   *Check* again, a second gives a fresh report with no bar text; redo
   brings *1 check added* back. Test:
   `ux01_criterion_3_undo_takes_a_check_back`.
4. The result matches `ux01-*` at 960 × 540 and 1600 × 1000: the QA report
   compares the five captures, on Linux and from the Windows CI artifacts;
   the verification commands of the development guide pass.
5. Added: the next run runs the checks. *Run simulation* after two checks
   gives a report with two more passed steps, no bar text, and every field
   offering *Check* again. Test:
   `ux01_criterion_5_the_next_run_runs_the_checks`.
6. Added: the board and the code keep the run while only checks were added:
   the cards' pass marks (`fresh_run`) are still shown after a check, and
   gone after another change. Test: `ux01_criterion_6_the_board_keeps_the_run`.
7. Added: a component's tab behaves the same on a component's own run
   (KTLO-23), in `component_run_tests.rs`'s setting. Test:
   `ux01_criterion_7_a_component_run_counts_its_checks`.
8. Added: the bar fits. At 960 × 540 maximised and restored, and at

9. Added: the gesture and the state are named in every test (planning.md's

## Technical appendix

- `folder/runs.rs`: `reports: HashMap<String, Report>` with `struct Report {
  prepared: PreparedRun, result: RunResult, checks: Vec<AddedCheck> }`,
  `AddedCheck { node_id, port, path, source_after: u64 }` — the hash of the
  document's text right after the check's edit applied. `apply_edit` →
  `component_action(Model)` applies synchronously (`publication.rs`), so
  `folder_report_action`'s `AssertField` arm records the hash from
  `session.document(id).text()` after it returns, when the node count grew.
- `enum Freshness { Fresh, ChecksOnly(usize), Stale }` computed in
  `run_report`: `Fresh` when `!session.run_is_stale(&prepared)`; otherwise
  `ChecksOnly(i + 1)` when the current text's hash equals
  `checks[i].source_after` for the latest such `i` and the other conditions
  of `run_is_stale` (`last_valid`, `fields`, `conflict`, `registry`) are
  clear; else `Stale`. Undo and redo fall out of the hashes: the text returns
  to an earlier `source_after`, or to the run's own source (`Fresh`).
- `report::Context`: `stale` keeps meaning `Stale`; new `checks_added:
  usize` and `checked: &[AddedCheck]` (or the three strings). `toggle_bar`
  shows the grey count when `checks_added > 0` and `!stale`, the amber text
  when `stale`. `value_branch`: a row whose `(node_id, port, path)` is in
  `checked` paints `Icon::Check` in `theme::SUCCESS` and *Check added* at
  `theme::FONT_LABEL` instead of the two buttons, as the mock-up's branch
  does. `document_locked` stays `stale || !editable`, so the policy combo
  and the remaining *Check* buttons work in `ChecksOnly`.
- `fresh_run(id)` returns the report for `Fresh` and `ChecksOnly` (the
  board's and the code's marks, criterion 6); its three callers keep their
  meaning. `component_run_tests.rs` criterion 3 (line 224) edits a default
  value, not a check, and keeps asserting *Graph changed*.
- The hash is `std::hash::DefaultHasher` over the text; it is never
  persisted. The mock-up's `mock_ux00` check list is not merged; the review
  view `review_ux01_two_checks` is rewritten against the real state and
  added to `testing::review`.
