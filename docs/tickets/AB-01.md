## Goal

"Definitely A/B of versions 0.1 and 0.2. What got worse will have to be
addressed." (owner, 2026-11-21). The same tasks of a functional tester
are done by agents in the window of the released v0.1.0 and of the
released v0.2.0; what is worse on 0.2.0 becomes a list of tickets the
owner confirms.

## What the owner will see

Nothing in the application. A page of results per round, and a list of
regressions with a class each, put to the owner in a quiz.

## Round 1, to be run unattended

The coordinator is an Opus session; each run is driven by a **fresh**
Opus subagent. The coordinator does not drive and does not class
anything: it sets up, briefs, checks, counts and writes the table.

### Setup, once

```bash
R=$(mktemp -d)                          # the round's folder; never the repository
for v in v0.1.0 v0.2.0; do
  mkdir -p "$R/$v" && gh release download "$v" -R jakubiszon26/apiforge \
    -p '*linux-gnu.tar.gz' -p SHA256SUMS.txt -D "$R/$v"
  (cd "$R/$v" && sha256sum -c --ignore-missing SHA256SUMS.txt && tar xzf ./*.tar.gz)
done
CARGO_TARGET_DIR=/home/jakub/Projekty/apiforge/target \
  cargo build --release --locked -p apiforge-demo-api
```

The application is `"$R/<v>/apiforge-<v>-x86_64-unknown-linux-gnu/apiforge-desktop"`,
its CLI `apiforge` beside it. A run is checked with **its own version's**
CLI.

### One run

1. `P="$R/run-<v>-<T>-<n>/proj"; mkdir -p "$P"` — an empty folder.
2. Start the demo API fresh and keep its process id:
   `/home/jakub/Projekty/apiforge/target/release/apiforge-demo-api & echo $! > "$R/demo.pid"`.
3. The driver starts the window through the `kwin` MCP server:
   `session_start` with `app_command` = the application and `--folder $P`,
   `isolate_home: true`, `screen_width: 1280`, `screen_height: 800`. It
   takes a screenshot and goes on only when the window shows *Open a
   folder project*; *Initialise project* is its first action and is not
   counted.
4. The driver does the task and calls `session_stop`.
5. `kill "$(cat "$R/demo.pid")"`, then the pass check below, with the
   demo API started again the same way for the check and stopped the same
   way after it.

**Never `pkill -f` or `pgrep -f`**, in the coordinator or in a driver: the
pattern matches the shell that runs it and kills the session. A process
is stopped by the id kept when it was started. No loop that waits on a
process list. If the `kwin` server is missing, the round is not run: say
so on the issue.

The order of the runs: T1 A, T1 B, T2 B, T2 A, then again starting with
B, then again starting with A; the shortest paths last.

### The driver's brief, word for word

> You are testing a desktop application as a functional tester who has
> never seen it. Do the task below in its window, using only the pointer
> and the keyboard through the `kwin` tools. Start the session exactly as
> given. Look at the window after every action that changes it; never
> send input you have not seen the target of.
>
> You may not: edit or read the project's files outside the window; use
> a terminal, the `apiforge` command or any `apiforge` MCP tool; read the
> application's source or documentation; open the *Code* view or the
> *Split* view. Never run `pkill -f` or `pgrep -f`. If you cannot go on,
> stop and say where.
>
> Keep a log, one line per action: its number; `click`, `drag`, `menu`,
> `type` or `scroll`; what you acted on, by its label; for `type`, the
> exact text; and `WRONG TURN` with what you expected when an action did
> not help and you gave it up. Mark a missed click or a wait too short
> as `DRIVER`. When you believe the task is done, save with the window's
> *Save*, take one screenshot, stop the session, and return the log and
> one sentence: done, or where you stopped.
>
> What a tester knows about the API: it is at
> `http://127.0.0.1:4318/demo`. `GET /shop/products/{id}` returns a
> product; product 123 exists. `POST /shop/carts` with a JSON body
> `{ "productId": …, "quantity": … }` creates a cart and returns it with
> its `id`. `GET /shop/carts/{id}` returns a cart. `DELETE
> /shop/carts/{id}` deletes it. Requests are to be really sent, not
> simulated.
>
> The task: ‹T1 or T2›

**T1.** "Make a new test that asks the shop for product 123, and run it
against the server until it passes."

**T2.** "Write a test that creates a cart with two of product 123, reads
the cart back by the id the API gave it, checks that it is the same cart
with the same quantity, and deletes it, checking that the delete worked.
Run it twice. Then make the delete happen even when a check fails."

The driver is told nothing else: not the version, not that versions are
compared, not what is expected.

### The pass check

With `A="$R/<v>/apiforge-<v>-x86_64-unknown-linux-gnu/apiforge"` and `F`
the one `.afs` under `$P/scenarios/`:

| | Passes when |
| --- | --- |
| Both | `"$A" check --folder "$P"` exits 0; `"$A" run --folder "$P" --scenario "scenarios/$F" --live --json` reports the run passed |
| T1 | the file has exactly one request, a `GET` whose address ends in `/shop/products/123`, and the run's step has status 200 |
| T2 | the file has a `POST` to `/shop/carts` whose body has `productId` 123 and `quantity` 2; a `GET` and a `DELETE` whose addresses read the `id` of the POST's response and hold no literal id; at least one check that reads the GET's response; the `DELETE` inside `cleanup`; and **the run command passes a second time** with nothing changed |

A T2 file whose first run passes and second fails is recorded as *done
after a wrong result*, with the check that failed. Whether the driver saw
it itself is in its log. The conditions are tried by hand on one file per
version before the first counted run; a condition that cannot be stated
for language 1 is reported, not bent.

### Counting

From each log, leaving `DRIVER` lines out: pointer actions (`click`,
`drag`, `menu`), text entries, characters typed, characters of language
syntax among them (a `{{…}}` placeholder, an operator, a handle typed
where a value is expected), scrolls, wrong turns with their place. A run
that broke a rule of the brief is void and repeated once; a second void
is reported.

The **shortest path** of a task on a version is the shortest passing
first-time run with its wrong turns removed, replayed by one more fresh
driver that is given the list of actions. For T2 on v0.2.0 the walk in
[REQ-06](REQ-06.md#the-scenario-against-v020-and-the-plan) is the
starting list. This departs from the process, where the planning model
writes the path: it has not seen v0.1.0's window, and it reads the paths
when it classes the results.

### Where the results go

A branch `docs/ab-01` from `main`, one pull request for the ticket, the
rounds added as they are run. `docs/qa/<date>/AB-01/round-1/`:

- `task.md` — the brief and the two tasks as given, the setup, the pass
  check.
- `results.md` — per task one table: rows *Done*, *Pointer actions*,
  *Text entries*, *Typed / syntax*, *Scrolls*, *Wrong turns*, *Wrong
  result*, *The diff* (lines of the file beyond the task); columns
  v0.1.0 and v0.2.0; in each cell the shortest path and the three runs,
  never an average. Under it the wrong turns, each with its version, its
  place and what the driver expected; the void runs; what could not be
  checked.
- At most three captures, of wrong turns a picture says faster.

No logs, no screenshots of every step, nothing from `$R`. The table is
also posted on #537. The coordinator states what differs between the
versions as counted; **it does not call anything a regression, give a
class, open an issue or change a label** — that is the next section, and
the planning model's and the owner's. It stops after round 1.

## Rounds 2 to 4

Decided by the owner on 2026-11-23 (#537): these rounds compare v0.1.0
with **the 0.2.1 candidate**, published as `v0.2.1-rc.2` (`rc.1` was
never published), so that what DIAG-08, DIAG-09, DIAG-10, UX-41, UX-42,
LANG-22 and DEMO-01 changed is not found again. Everything in *Round 1*
holds — the coordinator, fresh drivers, the brief, the counting, the
shortest path, no `pkill -f` or `pgrep -f`, no loop on a process list —
except what this section changes. One round is taken at a time, in the
order 2, 3, 4; each has its own branch `docs/ab-01-round-<n>` from
`main`, its own pull request and `docs/qa/<date>/AB-01/round-<n>/`. The
coordinator stops after its round.

### What changes from round 1

- **Builds.** `v0.1.0` and `v0.2.1-rc.2`
  (`apiforge-v0.2.1-rc.2-x86_64-unknown-linux-gnu.tar.gz`), downloaded
  and verified as in *Setup*. The tables' columns are *v0.1.0* and
  *v0.2.1-rc.2*.
- **No server.** The rooms API is fictional: every run and every check
  is a **simulation** on the saved samples, the CLI's `run` without
  `--live`. The demo API is neither built nor started, except for
  preparing T7's start.
- **The start is a prepared project**, not an empty folder: a copy per
  run of `crates/apiforge-cli/tests/fixtures/rooms-language-1` (v0.1.0)
  or `fixtures/scenarios/lay/rooms` (v0.2.1-rc.2), changed as the task's
  row below says, the same change in both. The window is started with
  `--folder` on the copy and the driver goes on when it shows the
  project. The fixtures in the repository are not touched. Before the
  first counted run the coordinator opens each prepared project in its
  version's window and runs its version's `check` and `run`; if v0.1.0
  does not open its copy, the round is not run and the issue says why.
- **Neutral paths**, as round 1 did: `$R/a`, `$R/b` for the builds and
  `$R/p<number>/proj` for the runs, so that a driver cannot read the
  version. The session start is a paragraph of the brief.
- **A scenario is named by its registered path** in
  `apiforge.project.json`, never by a folder.
- **The log is written as the driver goes**, one line before the next
  action; a log rebuilt afterwards makes the run void.
- **Captures.** Before `session_stop` the driver copies its screenshot
  of each wrong turn to `$R/captures/`; the coordinator commits at most
  three per round.
- **The pass check is a script**, `check.sh` beside `task.md`, which
  reads the `--json` snapshot and the file; it states what the task
  meant and not only its letter (round 1 passed a T2 result with two
  `DELETE`s). It is tried on a hand-made passing file and a hand-made
  failing one per version before the first counted run.
- **Known findings are counted, not classed again**: R1 (#547), R2
  (#548) and the *same on both* list of round 1's
  [classes](../qa/2026-11-21/AB-01/round-1/classes.md).
- The size stays 1280 × 800; a driver that maximises the window says so
  in its log.

### Order and budget

Per round the order of round 1: first task A, first task B, second task
B, second task A, then starting with B, then with A; the shortest paths
last. Sixteen runs. A round that reaches 90 minutes of agents stops and
reports what was run.

## From the results to tickets

1. The planning model lists, per task, what is worse on v0.2.0, what is
   better and what is the same, and proposes a
   [class](../process/ab-testing.md#regressions) for each regression.
2. A regression that an open issue already covers is linked to it, not
   filed again — DIAG-09 (#399), UX-41, UX-42, DEMO-01, REQ-11 to REQ-13
   and the other REQ tickets are checked first.
3. The owner confirms the list and the classes in a quiz.
4. Each confirmed regression becomes an issue: class 1 for 0.2.1, class
   2 for the next sprint, class 3 for the backlog. Only then is anything
   labelled.

Round 1 is classed in
[classes.md](../qa/2026-11-21/AB-01/round-1/classes.md) (2026-11-23): two
regressions proposed, class 2 and class 3, none of class 1; confirmed by
the owner on 2026-11-23 (#537): R1 is class 2 and went into REQ as
DIAG-15 (#547), R2 is class 3 in the backlog (#548).

Rounds 2 to 4 are classed together in
[classes.md](../qa/2026-11-23/AB-01/classes.md) (2026-11-23): no class 1
and no class 2; three of class 3 proposed (LAY-43 #466, #577, #578); T6
is not decidable, as round 4 made one run of it per version, and what it
showed is covered by DIAG-06b (#491). The findings that are the same on
both versions and had no issue are #574, #575, #576 and #579; the
planning model's own proposals are #580 and #581. The owner's
confirmation is open.
