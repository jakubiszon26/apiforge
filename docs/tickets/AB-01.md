- Size: M · Owner review: 20 min (the list of regressions) · Risk: none
  (no change to the product)
- State: **Analysis; not ready** — it waits for the owner's approval of
  the method ([A/B rounds](../process/ab-testing.md)) and for questions
  5, 8 and 9 of [REQ-06](REQ-06.md#questions-for-the-owner) · issue
  [#537](https://github.com/jakubiszon26/apiforge/issues/537)
- Analysis model: Fable 5.2 (the task sheets, the shortest paths, the
  results) · Drivers: Opus subagents · not taken unattended

## Goal

"Definitely A/B of versions 0.1 and 0.2. What got worse will have to be
addressed." (owner, 2026-11-21). The same tasks of a functional tester
are done by agents in the window of the released v0.1.0 and of the
released v0.2.0; what is worse on 0.2.0 becomes a list of tickets the
owner confirms.

## What the owner will see

Nothing in the application. A page of results with one table per task,
and a list of regressions with a class each, put to the owner in a quiz.

## Mock-up

Not applicable: no interface change.

compared with a key written beforehand.

## Runs and measures

The measures are those of the [process](../process/ab-testing.md#what-is-measured).
Per task and version: two first-time runs by fresh drivers, and the
shortest path where the two versions differ in how the task is done.
Eight tasks on two versions are about forty runs — more than one round's
budget, so AB-01 is **two rounds**: T1–T4 (building) and T5–T8 (reading,
diagnosing, rearranging), about two hours of agents each. Results:
`docs/qa/<date>/AB-01/`.

## From the results to tickets

1. The planning model lists, per task, what is worse on v0.2.0, what is
   better and what is the same, and proposes a
   [class](../process/ab-testing.md#regressions) for each regression.
2. A regression that an open issue already covers is linked to it, not
   filed again — DIAG-09 (#399), UX-41, UX-42, DEMO-01 and the REQ
   tickets are checked first.
3. The owner confirms the list and the classes in a quiz.
4. Each confirmed regression becomes an issue: class 1 for the next
   release, class 2 for the next sprint, class 3 for the backlog. Only
   then is anything labelled.

## Acceptance criteria

1. `task.md` holds the eight sheets, the start projects and the pass
   conditions, and a second model has read them for a hint of the answer.
2. Every counted run kept the driver's rules; void runs are named.
3. `results.md` has one table per task and the list of regressions, each
   with its class, its place in the window and a capture where a picture
   says it faster.
4. The owner's answer is recorded here, and each confirmed regression is
   an issue.

## When

Recommended (question 9 = A): now, in parallel with the 0.2.1 tickets,
finished before `v0.2.1-rc.1` is tagged. A class 1 regression can then
still enter 0.2.1, which exists to carry the owner's findings on 0.2.0;
the rest goes to REQ. Waiting until after 0.2.1 delays nothing in the
patch and leaves every regression for a release more. The failed tasks
are run once more on the candidate either way: it costs minutes.

## Not in scope

- Fixing anything found.
- Windows; a human tester's run.
- The MCP server and the CLI as ways of doing the tasks.
