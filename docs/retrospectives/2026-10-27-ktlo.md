# Retrospective: KTLO, keep the lights on (2026-10-25 to 2026-10-27)

- Period: 2026-10-25 20:12 (PR #1, the process documents) to 2026-10-27 18:28
  (PR #85, the last KTLO acceptance). Planned for 2026-10-26 to 2026-11-08;
  closed by the owner after two days because every ticket but this one was
  accepted.
- Outcome: a successful stabilisation sprint and a useful pilot of the
  [development process](../process/README.md). Scope control, product
  decisions and the quality of what reached `main` improved markedly against
  Stage II. The process proved too expensive for small tickets and its size
  rule does not measure what it was meant to; both are corrected by the
  actions below before the MCP sprint.

## What worked

- **Mock-ups and decisions before code.** Every interface ticket had captures
  the owner decided on; what was built matched what was approved. Zero ticket
  decisions were asked after code existed, against four of four in Stage II.
- **Decision cards.** A decision put to the owner as a short question with
  variants and a recommendation was answered in minutes and most
  recommendations were accepted. The owner accepted more changes per hour of
  their time than in any earlier period, and asks to keep the format.
- **Acceptance tests first, then the QA report.** Fifty-three `test` commits
  preceded their implementation. The reports said what was not verified, so
  the owner knew what a green report proved.
- **The sprint delivered.** The block library (panel, width, popup sections,
  rail, Files tab), one header above the board, the editor without a box,
  Problems and Run results that expand, running a component from its tab, the
  hidden open-files bar, migration of the owner's real workspace, the identity
  checkpoint decision, a green CI on both platforms, and the Stage II defects
  the new tests surfaced.
- **The repository is the record.** This retrospective was built from Git,
  the issues and the ticket files alone.

## What did not

- **The size class measured the wrong thing.** 15 of 19 code tickets left
  their class; 7 became `L`. Only a quarter of the changed lines is source
  code: the rest is acceptance tests, the QA report, the ticket file and the
  review views that the process itself requires. A 49-line change to
  checkpoint sealing (KTLO-04) carried 336 lines of tests and 267 of
  documentation; a 1 012-line animated dog (KTLO-20) carried no risk at all.
  The rule punished thorough tests and documentation and said nothing about
  what actually decides review effort: complexity, uncertainty, regression
  potential and the cost of verifying. Allowed by: `estimation.md` defines
  size by changed lines and makes the class a hard limit.
- **Tickets and pull requests were too fine-grained.** Five pull requests
  changed only a backlog row, a recorded decision or a sentence; seven more
  held an analysis whose implementation then needed a second pull request and
  a second wait. Each wait blocked the flow for the owner and the agent alike.
  Allowed by: "one ticket, one pull request" with no rule that the analysis,
  the decision, the tests and the implementation of one deliverable travel
  together.
- **Scope grew five times.** Ten of 27 tickets joined after the sprint
  started, 115 + 65 + 15 owner minutes of them by the owner's own decision.
  Each addition was decided and recorded, so this is not Stage II's drift,
  but the sprint had no reserved capacity for it and no rule that an addition
  displaces something. Allowed by: the backlog has exit criteria and
  estimates but no capacity line to compare the additions against.
- **The Windows smoke list never ran** and the exit criterion was ticked as
  done. Allowed by: nothing checks a ticked criterion against the evidence
  the ticket's report records.
- **Actual review minutes were never recorded**, so the one estimate that
  measures the real constraint cannot be compared with anything. Allowed by:
  the ticket template asks for the actual line at close and nothing enforces
  it.
- **The ignore rule has a hole.** 24 design-review views carry an
  `#[ignore]` without a ticket because they are never meant to run; the rule
  treats them as defects. Allowed by: `testing.md` knows one kind of ignore.
- **No path for a smaller model.** Every ticket, including a one-line demo
  fix, went through Fable for the analysis and Opus for the code, while the
  owner also has GPT 6.1 SOL available and would hand it approved, low-risk
  tickets. Allowed by: the model table knows Fable, Opus and Sonnet only and
  has no criterion for when a ticket is safe to hand off.

## What surprised us

- The sprint planned for two weeks closed in two days: with a one-page
  analysis and a decision card per ticket the owner's time, not the agent's,
  set the pace, and the owner could keep up.
- The acceptance tests found five Stage II defects that 961 green tests had
  not, three of them tests that passed or failed depending on the run.
- Interface findings arrived after acceptance even with mock-ups: the owner
  used the accepted change and found the scenario the mock-up did not show
  (dragging a panel instead of pressing its button; several checks instead of
  one). A static capture does not show interaction, and the criteria named
  the button, not the gesture.
- The red status line in the code editor, meant to say "the source is invalid
  and the board holds", reads to the owner as "there is an error in your
  code" while they are still typing. Nobody checked how a state indicator
  reads mid-edit.

## Interface findings carried into the MCP sprint

Raised by the owner on 2026-10-27 after using the accepted changes. They are
not retrospective actions: they are tickets for the MCP sprint planning, with
a shared mock-up that shows how they work together, and a capacity line of
their own in the sprint plan. In the owner's priority:

1. **Several checks from one run.** From Run results a check can be added for
   one field only; adding checks on more fields means a run per check.
2. **Run mode is a setting, not a menu item.** Run options chooses simulation
   or live and the choice persists; the main Run button runs the chosen mode
   and reads *Run simulation* or *Run live*; in simulation it is purple, as
   the simulation badge in Run results is.
3. **The editor's red status line goes.** While editing, the red line in the
   code editor suggests an error. Later, an error marks the exact lines; the
   line itself disappears now.
4. **"Running unsaved code" moves to the window header.**
5. **Run results and Problems drag to the whole workspace.** KTLO-19 and
   KTLO-18 maximise with a button; dragging the panel's edge is still
   stopped short. Dragging reaches the full workspace.

request that carries this document so that the MCP sprint is planned under
the amended rules.
